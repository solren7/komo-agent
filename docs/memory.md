# Agent Memory：面向 LLM Agent 的记忆架构说明

> 适用对象：产品负责人、Agent 平台/应用架构师、算法与工程团队  
> 目标：把“记忆”从聊天记录堆积，升级为可检索、可治理、可学习的决策能力。

## 一、结论先行

Agent Memory 不是单一的数据库，也不等于更长的 Context Window。它是一套围绕当前任务进行信息选择、组织、使用、学习与治理的系统。

一个成熟的 Agent Memory 系统应包含四类记忆：

| 记忆类型 | 回答的问题 | 在 Agent 中的典型内容 | 生命周期 |
|---|---|---|---|
| Working Memory（工作记忆） | 我现在正在处理什么？ | 当前目标、约束、计划、中间结果、已检索信息 | 秒至小时 |
| Episodic Memory（情景记忆） | 过去发生过什么？ | 历史对话、任务过程、工具调用、结果与反馈 | 天至年 |
| Semantic Memory（语义记忆） | 我长期知道什么？ | 用户偏好、稳定事实、实体关系、业务知识 | 较长期 |
| Procedural Memory（程序记忆） | 我应该如何做？ | Skills、工作流、策略、提示模板、操作规范 | 较长期 |

核心链路是：**长期记忆存储 + Retrieval（检索）+ Memory Controller（记忆控制器）+ Working Memory 管理**。系统能力的关键不在“存得多”，而在“在正确时机向当前推理加载正确的信息”。

---

## 二、四类记忆：定义与边界

### 2.1 Working Memory：当前决策周期内的活跃信息

Working Memory 是当前 Context 中，被持续维护、组织并直接参与下一步推理或行动的信息集合。它通常包括：

```text
Working Memory
├── Goal：当前目标与成功标准
├── Constraints：时间、权限、格式、预算、风险约束
├── Context：当前对话、文件、工具结果、环境状态
├── Scratch State：计划、待办、中间推理结果、已完成步骤
└── Retrieved Memory：本轮从长期记忆中临时取回的信息
```

例：用户要求“比较 Shopify、Shoplazza、BigCommerce 的国际化能力并给出建议”，工作记忆可包括比较维度、待验证项、已查证结论和最终输出格式。

### 2.2 Episodic Memory：可追溯的经历

Episodic Memory 记录一次互动或任务的上下文、过程和结果。它不应只保存原始聊天文本，也应保留可审计的事件：任务目标、工具调用、关键决策、产物位置、用户评价、失败原因等。

其价值是“复盘与个性化”：例如，知道某用户上次将 20 页竞品分析压缩为 5 页，并且特别关注支付与本地化。

### 2.3 Semantic Memory：稳定、可复用的事实与偏好

Semantic Memory 是从多次经历中提炼出的、具有一定稳定性的知识。典型内容包括：

- 用户偏好：偏好结论先行、输出简洁；
- 业务事实：某市场的支付方式、品牌与实体关系；
- 组织知识：术语定义、产品边界、政策规则；
- 环境知识：常用系统、权限范围、文件或项目结构。

它不是历史原文的简单摘要。每条事实应带有来源、置信度、更新时间和适用范围，避免把一次性的上下文误写成长期事实。

### 2.4 Procedural Memory：可执行的做法

Procedural Memory 指“如何完成某类任务”的稳定策略，最接近工程中的 Skills、Workflow、Policy、模板与工具调用规范。

例如，“撰写市场分析时：先给结论，再给市场规模、竞争格局、机会和证据；控制篇幅并标出假设”是一条程序记忆。它比知识事实更强调步骤、条件和质量标准。

## 三、认知概念与现代 LLM/Agent 工程概念的对应

| 认知概念 | 工程近似对象 | 说明 |
|---|---|---|
| Working Memory | 当前任务的活跃 Context、状态机、计划、工具结果 | 直接参与本轮决策；应有明确容量和优先级管理 |
| Episodic Memory | History、trace、event log、任务记录 | 保留“何时发生、做了什么、结果如何” |
| Semantic Memory | Profile、Memory、Knowledge Graph、RAG 文档库 | 保存相对稳定、可跨任务复用的事实与偏好 |
| Procedural Memory | Skills、Workflow、Playbook、Policy、Prompt Template | 保存可执行流程与约束，不等同于一般知识 |
| Retrieval | 搜索、筛选、重排、压缩与加载 | 从多种长期记忆中选出当前需要的信息 |
| Memory Controller | 写入、更新、遗忘、冲突处理和加载策略 | 控制记忆的质量、成本、隐私和可解释性 |

可以用以下工程视角理解：

```text
User Query
    │
    ▼
Memory Controller
    │
    ├── 检索 History / Episodic Memory
    ├── 检索 Profile / Semantic Memory
    ├── 匹配 Skills / Procedural Memory
    └── 形成 Working Memory
              │
              ▼
           LLM Reasoning
              │
              ▼
        Tool / Response / Action
```

## 四、Context 与 Working Memory：容器与功能的区别

Context Window 是模型一次可接收的 token 容器；Working Memory 是其中真正被激活、维护并服务于当前决策的信息结构。二者相关，但不能等同。

| 维度 | Context Window | Working Memory |
|---|---|---|
| 本质 | 模型输入容量与载体 | 面向当前任务的认知/系统状态 |
| 范围 | 可包含大量历史、文档、指令和无关内容 | 仅包含当前目标所需的高优先级信息 |
| 关注点 | 能放多少 token | 应放什么、如何组织、何时更新 |
| 主要风险 | 成本、截断、长上下文注意力稀释 | 遗漏关键约束、状态错误、上下文污染 |
| 优化手段 | 模型上下文长度、压缩 | 检索、摘要、优先级、状态机、淘汰策略 |

因此，即使 Context Window 扩展到百万 token，把全部历史塞进去也不等于拥有良好的工作记忆。更理想的模式是：

```text
大量长期信息
    │
    ▼  Retrieval + Ranking + Compression
当前任务最相关的少量信息
    │
    ▼
Working Memory
    │
    ▼
Reasoning / Action
```

## 五、Retrieval 与 Memory Controller：分别解决“取什么”和“如何管”

### 5.1 Retrieval：以当前任务为条件的选择器

Retrieval 的职责不只是向量搜索。一个有效的检索链路通常包括：

1. **任务理解**：识别目标、实体、时间范围、风险级别与输出要求；
2. **候选召回**：从情景、语义、程序记忆及外部知识中获取候选；
3. **相关性重排**：综合语义相似度、时效性、可信度、权限和用户偏好；
4. **压缩与去重**：形成带来源的短事实、约束或操作指令；
5. **注入工作记忆**：按优先级装载，避免 token 与注意力被无关信息占用。

检索质量应以任务完成质量衡量，而非仅以“召回了多少内容”衡量。关键指标包括：相关性、事实正确性、覆盖率、时效性、上下文成本和可解释性。

### 5.2 Memory Controller：记忆系统的治理层

Memory Controller 负责决定“何时读、何时写、何时更新、何时遗忘”。它是避免记忆系统失控的核心组件。

| 控制动作 | 典型规则 | 目的 |
|---|---|---|
| 写入 | 仅写入可复用、高价值、来源明确的信息 | 降低噪声与错误固化 |
| 提炼 | 从多次 episode 归纳 profile、事实或模式 | 将经历转化为知识 |
| 更新/冲突 | 新信息覆盖旧信息前先比较来源、时间与置信度 | 避免陈旧或矛盾事实误导决策 |
| 遗忘/过期 | 对低价值、敏感、过时信息设置 TTL 或删除策略 | 控制风险、成本与隐私 |
| 读取 | 根据任务和权限决定哪些记忆可加载 | 防止越权和上下文污染 |
| 审计 | 保留记忆来源、使用记录与变更历史 | 支持解释、纠错与合规 |

## 六、学习闭环：Experience → Memory → Action → Feedback

Agent 的长期改进不应依赖把每次对话原样保存，而应通过受控的记忆转化形成闭环：

```text
┌────────────┐
│ Experience │  对话、任务、工具调用、环境事件
└─────┬──────┘
      ▼
┌────────────┐
│ Episodic   │  保留可追溯的过程与结果
│ Memory     │
└─────┬──────┘
      ▼  归纳、验证、去重、加置信度
┌────────────┐
│ Semantic   │  形成稳定事实、偏好、实体与关系
│ Memory     │
└─────┬──────┘
      ▼  从重复成功/失败模式中抽象
┌────────────┐
│ Procedural │  形成 Skill、工作流、策略与检查项
│ Memory     │
└─────┬──────┘
      ▼  按任务检索并注入
┌────────────┐
│ Action     │  推理、回复、工具调用、执行任务
└─────┬──────┘
      ▼
┌────────────┐
│ Feedback   │  用户反馈、指标、人工审核、执行结果
└─────┴──────┘
      │
      └──────────── 回写、修正或淘汰记忆
```

这条链路需要明确区分“观察”与“结论”：一次用户表达是 episode；在多次一致证据下，才适合提炼为 profile 或稳定偏好；反复验证有效的做法，才适合固化为 workflow 或 skill。

## 七、建议的 Agent Memory Architecture

### 7.1 分层架构

```text
                         ┌──────────────────────────┐
                         │      User / Environment  │
                         └────────────┬─────────────┘
                                      ▼
┌─────────────────────────────────────────────────────────────────┐
│                    Orchestrator / Memory Controller              │
│  Task parsing · permission · read/write policy · conflict · TTL │
└───────┬─────────────────────┬─────────────────────┬─────────────┘
        │                     │                     │
        ▼                     ▼                     ▼
┌──────────────┐     ┌────────────────┐    ┌──────────────────┐
│ Working      │     │ Retrieval       │    │ Memory Writeback │
│ Memory       │◀────│ recall/rerank/  │    │ extract/validate │
│ goal/state/  │     │ compress/cite   │    │ update/expire    │
└──────┬───────┘     └───────┬────────┘    └────────┬─────────┘
       │                     │                      │
       ▼                     ▼                      ▼
┌──────────────┐  ┌────────────────┐  ┌──────────────────┐
│ LLM + Tools  │  │ Episodic Store │  │ Semantic Store   │
│ action loop  │  │ history/traces │  │ profile/knowledge│
└──────────────┘  └────────────────┘  └──────────────────┘
                                      ┌──────────────────┐
                                      │ Procedural Store │
                                      │ skills/workflows │
                                      └──────────────────┘
```

### 7.2 各层职责

| 层级 | 职责 | 推荐实践 |
|---|---|---|
| Interaction & Orchestration | 识别任务、权限与风险；驱动状态机 | 明确任务 ID、用户/租户边界、成功标准 |
| Working Memory | 持有当前任务的最小充分状态 | 使用结构化字段，不把所有历史原文塞入 prompt |
| Retrieval | 跨记忆类型选择、重排、压缩与引用 | 混合检索：关键词、向量、图谱、时间和权限过滤 |
| Episodic Store | 保存事件、trace、产物、反馈 | 事件化存储，支持按任务/实体/时间回放 |
| Semantic Store | 保存事实、偏好、关系与置信度 | 为每条记忆记录 source、scope、confidence、updated_at |
| Procedural Store | 保存技能、策略、工作流与检查清单 | 版本化、可评测、可回滚；不把业务事实硬编码进 Skill |
| Governance & Observability | 审计、权限、保留、删除、评测 | 记录“哪条记忆影响了哪次行动” |

### 7.3 建议的最小记忆对象

```yaml
memory_id: mem_...
type: semantic | episodic | procedural
content: 用户偏好先给结论，再提供证据
scope: user:xxx                 # 也可为 tenant / project / global
source: conversation:...        # 可追溯来源
confidence: 0.82
valid_from: 2026-08-16
expires_at: null
privacy: internal
status: active | superseded | deleted
```

## 八、关键设计原则

1. **任务优先，而非存储优先**：从“当前任务需要什么”反推记忆模型、检索和容量预算。
2. **最小充分加载**：只将完成当前任务所需的高价值信息放入工作记忆，控制上下文污染。
3. **分层且可追溯**：不要把历史、事实、偏好和流程混为一个向量库；每条记忆均应可定位来源。
4. **先验证，再固化**：一次对话不应自动变成长期事实或用户偏好；提炼需要证据、置信度和更新规则。
5. **时间与范围是一等字段**：事实会过期，偏好有适用场景；必须记录时效、用户/组织/项目边界。
6. **检索优先级高于存储规模**：存储无限增长不会自然提升质量；真正的瓶颈通常是召回、重排与压缩。
7. **程序记忆需版本化与评测**：Skills/Workflow 的改动可能直接改变行动，应具备测试、灰度与回滚机制。
8. **隐私、权限与删除默认内建**：记忆读取和写入都需要按主体、租户、数据等级和保留策略治理。
9. **把反馈连接到记忆变更**：用户修正、失败结果和人工审核必须能触发回写、降置信度或淘汰。
10. **以端到端结果评估**：评估“记忆是否使任务更正确、更一致、更省成本”，而非只看检索命中率。

## 九、未来研究方向

| 方向 | 关键问题 | 对产品/架构的意义 |
|---|---|---|
| 长时程记忆评测 | 如何衡量跨周、跨月任务的记忆正确性与收益？ | 从单轮 benchmark 转向真实任务成功率 |
| 主动记忆管理 | Agent 何时应询问、写入、遗忘或请求确认？ | 降低错误固化和隐私风险 |
| 记忆可信度与冲突消解 | 多源事实如何证明、合并和撤销？ | 提升高风险场景的可控性 |
| 个性化与共享知识隔离 | 用户偏好、团队知识、全局知识如何安全共存？ | 支撑企业级多租户部署 |
| 程序记忆的自动改进 | 如何从成功/失败轨迹中生成、验证和升级 workflow？ | 让 Agent 从“会回答”走向“会做事” |
| 多模态与具身记忆 | 图像、语音、界面操作、空间与环境状态如何统一表示？ | 支撑复杂工具操作与现实世界任务 |
| 因果与反事实记忆 | 如何区分“相关经历”与“真正有效的做法”？ | 减少错误经验迁移 |
| 可解释与可撤销 | 用户能否查看、修正、删除某条记忆及其影响？ | 构建信任、合规和可运营性 |

## 十、落地建议：从最小可用系统开始

若从零建设，建议按以下顺序推进：

1. 建立结构化的任务状态与 Working Memory，先保证当前任务不失控；
2. 记录可审计的 Episodic Trace，包括目标、关键行动、结果和反馈；
3. 在人工可见、可编辑的前提下提炼少量 Semantic Memory（如用户偏好、项目事实）；
4. 将已验证的高频流程固化为 Procedural Memory，并进行版本化评测；
5. 引入 Memory Controller，完善读写策略、置信度、过期、权限与审计；
6. 以真实任务成功率、返工率、上下文成本和用户纠错率持续优化。

最终目标不是让 Agent “记住一切”，而是让它在每个决策时刻，可靠地记住**足够且正确的事**。
